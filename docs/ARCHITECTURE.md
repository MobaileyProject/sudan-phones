## Layer separation per domain

Maintain strict dependency direction: `HTTP View -> Serializer -> Domain Service -> Model`.

| Layer | Responsibility | Allowed | Forbidden |
| --- | --- | --- | --- |
| **HTTP** | `views.py` / `views/<domain>.py` | Request parsing, view logic, DRF permissions, HTTP status mapping | Direct SQL queries, raw ORM mutations, domain policies |
| **Contract** | `serializers.py` / `serializers/<domain>.py` | DRF serializers, field validation, strict request/response shapes | Direct DB queries, business orchestration |
| **Domain** | `services.py` / `services/<domain>.py` | Domain rules, ownership/authorization checks, atomic transactions (`transaction.atomic()`) | HTTP-specific exceptions, request/response objects |
| **Persistence** | `models.py` / `models/<domain>.py` | Django ORM entities, relationships, constraints, indexes | Endpoint logic, service orchestration |

Views call domain services; services orchestrate business invariants and transactions; models define declarative persistence and constraints. Services enforce store-scoped permissions even when invoked outside HTTP handlers.

Use Python 3.13 (the CI/runtime target) and PostgreSQL 16. Django migrations manage database schema evolution. Review migration operations against PostgreSQL 16; do not substitute SQLite for PostgreSQL concurrency, locking or constraint behavior.

## OpenAPI contract lifecycle

The backend entry point is `backend/manage.py` configured with `drf-spectacular`. Export must not connect to live databases or depend on production secrets.

- `make openapi` writes stable sorted JSON to `docs/openapi.json`.
- `make openapi-check` compares generated bytes with the committed contract and fails for missing/stale JSON, import errors, or drift.
- CI installs `backend/requirements.txt` with pinned dependencies and verifies contract drift via `make openapi-check`.
- Every endpoint/schema PR regenerates the contract and updates `docs/api/<domain>.md`: method/path, business rules, caller permissions, fields, status/error meanings, and request/response examples. Link blueprint screen IDs (C-xx/M-xx/A-xx) to contracts and acceptance tests.

## Verification boundaries

- `make check`: secret scan, standard-library tool tests, Python compilation (`compileall`), JSON syntax, shared skills check, OpenAPI drift check, Django system checks (`manage.py check`), and backend tests (`manage.py test core`).
- Real PostgreSQL 16 tests verify migrations and database connectivity when `POSTGRES_DB` or `DATABASE_URL` is configured.
