# Architecture and API Contracts

## Status and precedence

This is the target architecture requested by the founders, not a claim that a
backend already exists. The local product PDF chooses Django/Flutter/React; the
explicit workspace setup request chooses FastAPI/Kotlin/Web Preview and takes
precedence for this setup. Confirm the discrepancy before application scaffolding.
The canonical operating rules are in [AGENTS.md](../AGENTS.md).

## Five layers per domain

| Path under `backend/app/` | Allowed | Forbidden |
| --- | --- | --- |
| `routers/<domain>.py` | HTTP endpoints, query/body parameters, DI, status/error mapping, response schemas | SQL queries, ORM access, domain policies |
| `schemas/<domain>.py` | Pydantic validation, explicit constraints, request/response shapes | Database I/O, business orchestration |
| `services/<domain>.py` | Domain rules, ownership/authorization checks, transaction begin/commit/rollback | HTTP-specific exceptions, request/response objects |
| `repositories/<domain>.py` | SQLAlchemy 2 selects/writes, joins, pagination, flush where needed | HTTP exceptions, authorization policies, commit/rollback |
| `models/<domain>.py` | Declarative ORM entities, relationships, keys, constraints, indexes | Endpoint logic, service orchestration |

HTTP -> service -> repository -> ORM is the runtime dependency direction. Schemas
form the boundary. Services return explicit results and domain errors, not raw
query/session objects. Dependency injection supplies sessions and caller identity;
services enforce permissions even when called outside HTTP. Keep repositories
store-scoped where applicable and test cross-store access at the service boundary.

Use Python 3.13 and PostgreSQL 16. Alembic must have exactly one migration head;
coordinate migration edits across agents and review migration upgrades/downgrades
against a real PostgreSQL instance. Do not substitute SQLite integration tests for
PostgreSQL concurrency, constraints, or locking behavior.

## OpenAPI contract lifecycle

The future backend entry point is `backend/app/main.py` exposing `app` with an
`openapi()` method. Export must not connect to live databases or depend on secrets.
If the backend later chooses a different entry point, update the exporter and CI
in the same PR.

- `make openapi` writes stable sorted JSON to `docs/openapi.json`.
- `make openapi-check` compares generated bytes with the committed contract and
  fails for missing/stale JSON, import errors, or an incomplete backend scaffold.
- Before any backend Python code exists, both commands explicitly report a skip;
  `docs/openapi.json` is deliberately absent rather than a placeholder contract.
- CI installs `backend/requirements.txt` if present. The first backend PR must add
  that file with pinned runtime dependencies (or replace this CI step with the
  chosen locked dependency install) so export succeeds on a clean runner.
- Every endpoint/schema PR regenerates the contract and updates
  `docs/api/<domain>.md`: method/path, business rules, caller permissions, fields,
  status/error meanings, and request/response examples. Link PDF screen IDs
  (C-xx/M-xx/A-xx) to contracts and acceptance tests.

## Verification boundaries

Current `make check`: secret scan, standard-library tool tests, Python compilation,
JSON syntax, and OpenAPI drift checks. This foundation has no backend, Android, or
web runtime. Each application scaffold must add its own lint/type/test/build jobs;
passing foundation checks does not certify a marketplace implementation.
