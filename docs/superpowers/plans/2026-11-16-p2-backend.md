# P2 Backend and Joint Acceptance Implementation Plan

**Goal:** Complete BE-02 and the backend evidence for INT-02, delivering one PR.
**Architecture:** Django/DRF views validate query serializers, call read-only
bootstrap services and serialize explicit public responses. Shared middleware and
exception handling provide JSON errors and request IDs. No frontend is added.
**Spec:** `docs/plans/ORDERED_STEP_BY_STEP_PLAN.md`, Phase 2; `SPEC-SCOPE-01`;
`docs/api/CATALOG_POLICY.md`.

## Constraints and decisions

- Preserve the merged Django/DRF dependencies and SDG/three-city pilot invariants.
- Canonical paths have no trailing slash: config, i18n/bundle and health under
  `/api/v1`. Config and bundle support `locale=ar|en`; otherwise negotiate
  Accept-Language with Arabic fallback. Invalid/duplicate/unknown query fields
  produce 400. GET/HEAD/OPTIONS only; no authentication or database reads.
- Success uses `data`; errors use `error.code/message/details`. Request IDs are
  server generated and returned in X-Request-ID. Public metadata contains no
  credentials, store evidence or customer data.
- Localization bundles cover bootstrap/loading/offline/error UI only. They do
  not claim complete future client translations. Arabic is RTL; English is LTR.
- INT-02 backend checks can pass independently; full phase acceptance requires
  actual Flutter/React build and real-client evidence, outside this request.
- Current API catalog is generated from registered OpenAPI operations. Preserve
  API-019/config and API-021/bundle; API-061 is liveness. Move unimplemented
  blueprint operations into planning. Slack current catalog changes only for
  merged code; retain future requirements in planning.

## Review focus

secret leakage; locale-aware cache headers without session cookies; catalog drift
when routes change; honest joint-gate reporting while frontend is absent.
